Migrar Paragraphs de Contenidos con Migrate

Drupal
Migrate

¿Cómo saben las aves cómo migrar? - The Daily Illini

Pablo Urrea

Lectura de 20 minutos
Publicado
18/03/2024
Actualizado
29/05/2024

La migración de contenido entre diferentes versiones de Drupal puede ser una tarea desafiante, especialmente al enfrentarse a cambios en la estructura de datos como la introducción de Paragraphs. Este proceso requiere un enfoque meticuloso y profundo conocimiento de las relaciones entre entidades. Con una comprensión sólida y las herramientas adecuadas, las migraciones exitosas son alcanzables.

El otro día me propusieron migrar contenidos de una web en Drupal 7 a otra en Drupal 10 sencillamente porque era más sencillo renovarla que actualizarla. Y yo, todo un experto en decir que si sin saber el pantano en el que me estaba metiendo, empecé a analizar de qué forma podía hacerlo.


En busca de la iluminación. Entre tanto, surgió construir una vista en el Drupal 7 que proporciona absolutamente todos los campos de un tipo de contenido en formato JSON. Hasta aquí parece sencillo ¿No?, configuras un archivo YML de migrate con los plug-ins adecuados y ya está, las entidades las tenía copiadas de un sistema a otro. Resulta que la estructura de datos ha cambiado en los últimos 10 años (Menuda sorpresa) y ahora ciertos bloques de contenidos que antes se almacenaban en la propia entidad, se almacenan como entidades de tipo Paragraph. Pensé, vale, migro las entidades Paragraph, añado la migración como dependencia de la entidad principal y le añado el plug-in de migración, y aquí no ha pasado nada. Entonces aquí me encontré con una maravillosa bi direccionalidad: La entidad padre necesitaba tener el Paragraph referenciado, y el Paragraph necesitaba tener la entidad padre referenciada (junto a otros datos del padre).

El problema era que no podía migrarlo así con el plug-in por defecto de migrate, ya que este solo añadía la referencia en una de las entidades: Si agregaba el Paragraph como dependencia de la entidad, esta no tenía referenciada al padre, y viceversa. Tres largos días duró esta batalla, hasta que di con una solución digna de Miguel Ángel (Por lo de esculpir y todo eso): Cincelar la base de datos cuando se migren Paragraphs para que ambas entidades casarán.


NOTA: El proceso de migración de entidades con la inclusión de paragraphs es una tarea compleja que requiere un enfoque meticuloso y una comprensión profunda de la estructura de datos y las relaciones entre entidades. En esta extensión, profundizaremos en los diferentes aspectos involucrados en este proceso, desde la identificación de los párrafos asociados hasta la actualización de la base de datos y la verificación de la integridad de los datos migrados.

 

Manos a la obra. Para poder tener todos los datos post migración lo mejor era crear un Event Subscriber, empezando por la configuración básica en el archivo module.services.yml:

services:
 module.migration_finished_subscriber:
   class: Drupal\module\EventSubscriber\MigrateParagraphsEventSubscriber
   tags:
     - { name: event_subscriber }

Y su correspondiente clase en el archivo src/EventSubscriber/MigrateParagraphsEventSubscriber.php:

class MigrateParagraphsEventSubscriber implements EventSubscriberInterface {
  public static function getSubscribedEvents() {
    $events[MigrateEvents::POST_IMPORT][] = ['postImport'];
    return $events;
  }
  public function postImport(MigrateImportEvent $event) {
  }
}

Con esta configuración y una limpieza de cachés, tras ejecutar cualquier migración, se ejecutará el código del método postImport.

 

Dejando migas de pan. Ahora, hay que identificar los procesos de migración de Paragraph en la entidad padre, para poder tener consolidadas en base de datos ambas entidades: La entidad padre, y el Paragraph.

Para ello, lo más sencillo es añadir una propiedad identificativa al proceso:

field_paragraphs/target_id:
  plugin: migration_lookup
  migration: module_migrate_paragraphs
  migrate_paragraphs: true
  source: id

De esta configuración se obtendría el ID de las entidades migradas en la primera migración (Los Paragraphs) basadas en un ID común de la fuente de datos, con la propiedad agregada migrate_paragraphs: true para identificar en el proceso que este proceso requiere casar las entidades Paragraph de la anterior migración con las migradas en la configuración actual.


Ensuciarse las manos. Ahora habría que identificar los campos que requieren de una migración de Paragraph. Para ello hay que obtener del evento el objeto de migración, y el proceso de esta en formato array:

$migration = $event->getMigration();
$migration_process = $migration->getProcess();

Ahora llega lo divertido, “procesar el proceso”:

protected function searchMigrationParagraphKeyValueInProcessArray(array $values, string|int $key = 0, string $value = ''): mixed {
  foreach ($values as $vkey => $vvalue) {
    if ($vkey === $key && $vvalue == $value) {
      return $vkey;
    }
    else {
      if (is_array($vvalue)) {
        $found = $this->searchMigrationParagraphKeyValueInProcessArray($vvalue, $key, $value);
        if ($this->paragraph_path_found === TRUE) {
          $this->paragraph_fields[$vkey] = [
            'field' => $vkey,
            'migration' => $found,
          ];
          $this->paragraph_path_found = FALSE;
        }
        if ($found === $key) {
          $this->paragraph_path_found = TRUE;
          return (!empty($vvalue['migration'])) ? $vvalue['migration'] : $values;
        }
      }
    }
  }
  return '';
 }

Este maravilloso método itera recursivamente sobre todos los procesos en array, y guarda el nombre del campo de los que contienen la propiedad migrate_paragraphs: true en la lista $this->paragraph_fields.

Pastilla roja, pastilla azul. Es importante tener en cuenta que este proceso únicamente nos ha proporcionado el ID de la entidad, que puede ser de cualquier tipo, para ello se ha de parsear desde la configuración del plugin destino o Destination Plug-in el ID del tipo de entidad sobre el cual debemos cargar el ID que hemos obtenido. Para ello hay dos métodos, uno más fiable que el otro, aunque para este ejemplo he incluido ambos para asegurar su obtención. El primer método consiste en obtener mediante expresión regular el valor del ID del Destination Plug-in el valor más a la derecha, coincidiendo en el 99,99% de los casos (Fuente: Times New Roman) con el tipo de entidad, por supuesto, en la mayoría de los casos coincidiendo con el valor “node”. Para verlo mejor, la expresión regular obtiene el valor resaltado de “entity:node”, haciendo posible mediante Entity Type Manager obtener el nodo por su ID. De no ser posible este proceso, el Entity Type Manager lanzaría una excepción en la que procesaremos el segundo método menos fiable: Obtener el proveedor de la definición del Destination Plug-in, este método puede fallar en el caso de sub entidades como Paragraphs, por eso lo mejor es comenzar por el primer método. El try-catch definido en el siguiente bloque explica cómo implementar ambos métodos y recurrir al segundo en caso de fallo del primero:

Conclusión. La migración de contenido, especialmente cuando implica entidades complejas como los Paragraphs en Drupal, puede ser un proceso desafiante. Sin embargo, con una comprensión sólida de los procesos involucrados y las herramientas disponibles, es posible realizar migraciones exitosas.

Actualización del 9 de mayo de 2024

Desde que publiqué este artículo (y previamente realizado este desarrollo) se me quedó clavada una espina de mejora de código. Por eso mismo hemos decidido hacer pruebas reescribiendo el método searchMigrationParagraphKeyValueInProcessArray() desde cero.


Lo más sencillo es lo más eficiente. Realmente, la mejor forma de evitar el uso de atributos de clase es utilizando la propia recursividad del método simplificado al extremo para que la propia recursividad no retrase el proceso:

protected function searchMigrationParagraphKeyValueInProcessArray(array $values, string $value, string $field = '', string $key = 'migrate_paragraphs'): array {
   $paragraphs_found_list = [];
   foreach ($values as $vkey => $vvalue) {
     if (is_array($vvalue)) {
       if (is_string($vkey) && strlen($vkey) > 0) {
         $field = $vkey;
       }
       $paragraphs_found_list = array_merge($paragraphs_found_list, $this->searchMigrationParagraphKeyValueInProcessArray($vvalue, $value, $field, $key));
     }
     elseif ($vkey === $key && (string) $vvalue === $value && isset($values['migration']) && is_string($values['migration'])) {
       $paragraphs_found_list[$field] = [
         'migration' => $values['migration'],
       ];
       continue;
     }
   }
   return $paragraphs_found_list;
 }

Actualización del 29 de mayo de 2024

Tras realizar múltiples pruebas de migración de distintos tipos de entidades, hay casos en los que se producía un error en la fila o row porque se había saltado la entidad en diferentes escenarios (traducción de entidades, paragraphs anidados, etc.), algo que me he dignado a corregir.


Es mejor dejar ir que aferrarse al error fatal. En realidad depurar código es muy saludable y ahorra bastante tiempo (aunque no siempre guste), esto me llevó al último bloque de código, donde se cincela la base de datos para que el paragraph no quede huérfano y se actualiza la entidad padre para que no se quede sin hijo. En casos específicos donde no encuentra el ID del hijo, intenta actualizar ambos y ahí termina el proceso, perdiendo la entidad y poniendo en riesgo la continuidad de la migración.

                    if (!empty($paragraphs)) {

                        if (!empty($paragraphs_source_data->{$this->migrate_db_target_id_column})) {

                          // This is used only to define if the Paragraph translation is the default translation.

La mejor solución lleva implementada mucho tiempo. Lo mejor para detectar errores y continuar la migración sin mayor incidencia es implementar en este caso un try-catch tanto en el cincelado de la base de datos, como en la actualización de la entidad padre. Pero yendo un paso más allá, y mejorando el sistema para que realice un menor número de actualizaciones de base de datos, el cincelado de esta se puede incluir tras validar la existencia del paragraph, evitando así repeticiones y actualizaciones innecesarias, reemplazando el bloque anterior por:

                    if (!empty($paragraphs)) {
                      foreach ($paragraphs as $paragraphs_source_data) {
                        if (!empty($paragraphs_source_data->{$this->migrate_db_target_id_column})) {
                          /** @var \Drupal\paragraphs\ParagraphInterface|null $paragraph */
                          $paragraph = Paragraph::load($paragraphs_source_data->{$this->migrate_db_target_id_column});
                          // For security reasons, check that the reference to the Paragraph
                          // in the entity field is not duplicated and consolidate its reference.
                          if ($paragraph instanceof ParagraphInterface && $entity->hasField($field_name) && !$this->isParagrahDuplicated($entity, $paragraph, $field_name)) {
                            try {
                              // It is assumed that website's default language is the same as the entity's default language.
                              // This is used only to define if the Paragraph translation is the default translation.
                              /** @var \Drupal\Core\Language\LanguageInterface $default_language */
                              $default_language = $this->language_manager->getDefaultLanguage();
                              $default_language_id = $default_language->getId();
                              $entity_langcode = ($entity->hasField('langcode') && $entity->langcode->value) ? $entity->langcode->value : 'und';

                              // Update the Paragraph values to have the entity field as parent.
                              $this->database->update('paragraphs_item_field_data')
                                ->fields([
                                  'langcode' => $entity_langcode,
                                  'parent_id' => $source_data->{$this->migrate_db_target_id_column},
                                  'parent_type' => $entity_type,
                                  'default_langcode' => ($default_language_id == $entity_langcode) ? 1 : 0,
                                  'parent_field_name' => $field_name,

Dentro del catch, se puede observar la implementación del sistema logger de Drupal, para añadirlo es tan sencillo como añadir el servicio @logger.factory al event subscriber en el archivo services.yml, agregar la dependencia Drupal\Core\Logger\LoggerChannelFactory al event subscriber, incluir dentro de este el objeto para registrar errores

 /**
  * The logger channel.
  *
  * @var \Drupal\Core\Logger\LoggerChannelInterface
  */
 protected $logger;

y actualizar el constructor de la clase para que este asocie el servicio al objeto:

  /**
   * Constructor.
   *
   * @param \Drupal\Core\Database\Connection $database
   *   The database connection.
   * @param \Drupal\Core\Logger\LoggerChannelFactory $logger
   *   The logger channel.
   * @param \Drupal\Core\Language\LanguageManagerInterface $language_manager
   *   The language manager.
   * @param \Drupal\Core\Entity\EntityTypeManagerInterface $entity_type_manager
   *   The entity type manager.
   */
  public function __construct(Connection $database, LoggerChannelFactory $logger, LanguageManagerInterface $language_manager, EntityTypeManagerInterface $entity_type_manager) {
    $this->database = $database;
    $this->language_manager = $language_manager;
    $this->logger = $logger->get('module');
    $this->entity_type_manager = $entity_type_manager;
  }

Este último paso es opcional, si no se desea tener un registro de fallos durante la migración, simplemente se puede dejar vacío el catch.
