La caché back-end personalizada de Drupal

Drupal
Caché

Pablo Urrea

Lectura de 15 minutos
Publicado
21/03/2025

En Drupal, la caché más utilizada es la que afecta al front-end, de forma que las páginas se cachean o guardan temporalmente hasta que un elemento dinámico cambia afectando al renderizado de la página, pero esto también es posible replicarlo en el back-end gracias a la caché de back-end, esto es útil, por ejemplo, cuando se actualizan los datos de una entidad para solicitarla de nuevo a la hora de renderizar una página. Pero ¿Qué ocurre cuando el proceso no tiene una conexión directa con el front-end o requiere un tratamiento de caché individualizado?

 

 

Interfaz de cacheado del back-end. Pongamos un ejemplo muy sencillo, una página contiene un bloque que llama a un servicio personalizado para solicitarle los estados de un nodo de tipo “Solicitud” y finalmente muestra la cuenta total de las solicitudes que están según un campo en “Borrador”, “Presentada”, “En trámite”, “Aceptada” o “Denegada”. Para ello el servicio obtiene todos los trámites del sistema y suma valores a cada estado para poder mostrar la cuenta total, hasta aquí fácil. Para el sistema también es fácil si sólo tiene que comprobar 100 solicitudes, pero ¿Qué sucede si en el sistema hay 10000 solicitudes? El sistema tarda demasiado en responder y se cae la página final, porque el servicio ha tardado demasiado en obtener y comprobar el estado de todas y cada una de las solicitudes. ¿La solución? Primero realizar una consulta a la base de datos para obtener directamente los nodos correspondientes por cada estado, lo segundo, cachear la respuesta hasta que uno de estos nodos cambie. Para ello es necesario implementar la interfaz de cacheado del back-end o CacheBackendInterface, esta se puede integrar directamente con

/** @var \Drupal\Core\Cache\CacheBackendInterface $cache */
$cache = \Drupal::cache();

O también se puede inyectar como dependencia con el argumento “@cache.default”.

  

¡A cachear resultados! Una vez implementada la interfaz de cacheado del back-end hay que cachear la variable, esta puede ser de cualquier tipo, ya que Drupal por detrás la va a serializar para guardarla. Para empezar hay que definir un ID de caché, es recomendable seguir el patrón MÓDULO:FUNCIONALIDAD/SERVICIO/CLASE:USO_FINAL/MÉTODO:ID_DE_LA_ENTIDAD/UUID_DE_LA_ENTIDAD:IDIOMA_SI_APLICA. Por ejemplo, un ID claro y conciso sería my_site_tramites:resumen_block:conteo_total:999:es, haciendo referencia al módulo personalizado my_site_tramites donde se encuentra la funcionalidad, el bloque resumen_block donde se encuentra la funcionalidad, la funcionalidad conteo_total, el ID 999 de la página padre donde se encuentra este bloque y el idioma es aplicable a la página.

Después hay que comprobar si existe algún elemento cacheado con este ID de caché, si lo hay, su valor será almacenado en $cache_item en el siguiente ejemplo para retornarlo o procesarlo ligeramente:

if ($cache_item = $cache->get($cid)) {

Si no lo hay, posterior a este if se realiza el procesamiento de datos y su cálculo se guarda en caché con

$cache->set($cid, $data, Cache::PERMANENT, $cache_tags);

Pero vamos a desgranar los parámetros proporcionados para entender mejor cómo obtenerlos correctamente y proporcionarlos al método set.

 

ID de caché. El ID único de la caché que va a ser almacenada, su valor en string puede ser cualquiera, pero para mantener un orden es mejor seguir un patrón similar al mencionado anteriormente.

 

Datos a cachear. Puede ser de cualquier tipo, string, integer, float, array, object (Cuidado con objetos muy densos que puedan superar el límite de memoria de la base de datos al ser serializados). Todo lo que guardes aquí será recuperado al solicitar la caché con el mismo ID.

 

Caducidad. Este valor puede ser cualquier número entero entre -1 e infinito donde -1 significa que la caché nunca caduca a menos que caduquen las etiquetas de cacheado, que comentaré en el próximo punto; 0 significa que la caché no se guarda nunca, porque caduca en el momento; y cualquier otro número es el timestamp en el que la caché quedará inválida, por ejemplo, el timestamp del 21 de marzo del 2025 a las 14 horas GMT es 1742565600. Como guía, las constantes más usadas son:

\Drupal\Core\Cache\Cache::PERMANENT

y

\Drupal\Core\Cache\CacheBackendInterface::CACHE_PERMANENT

Ambas con valor de -1.

 

Etiquetas de cacheado. Son etiquetas por las cuales el sistema identifica elementos como entidades y otros recursos para relacionarlos con otros elementos que dependen de su caché. Por ejemplo, la caché de un nodo con ID 25 sería node:25, cuando ese nodo rompe sus cachés porque es actualizado, todos los elementos con la etiqueta de caché node:25 deben ser recargados (Junto con el resto de la página). El método set de la caché back-end acepta una lista de cadenas de caracteres como último parámetro, esta lista se suele iniciar como array al comienzo del procesamiento, y en cada interacción con, por ejemplo un nodo, se llama al método de la entidad getCacheTags() para obtener un array con las etiquetas de caché de esta entidad, junto con el método de la clase auxiliar \Drupal\Core\Cache\Cache::mergeTags() al cual se le puede pasar cualquier número de arrays de caché tags y las unirá en una sola, algo así:

$cache_tags = \Drupal\Core\Cache\Cache::mergeTags($cache_tags, $node->getCacheTags());

Y finalmente proporcionando $cache_tags a la caché de back-end.

 

 

Conclusión. El uso adecuado y estratégico de la caché en el back-end de Drupal es fundamental para optimizar el rendimiento del sistema, especialmente cuando se manejan grandes volúmenes de datos. Implementar CacheBackendInterface permite almacenar y recuperar datos eficientemente, reduciendo la carga de procesamiento y mejorando la velocidad de respuesta de las páginas. Siguiendo buenas prácticas como el uso de identificadores de caché bien estructurados, una gestión adecuada de la caducidad y la utilización de etiquetas de cacheado, es posible garantizar que los datos almacenados sean precisos y actualizados cuando sea necesario. Con una estrategia de cacheado bien implementada, se puede mejorar significativamente la experiencia del usuario y la estabilidad del sistema sin comprometer la integridad de la información.
