Definición del tipo de dato weight en Drupal

Pablo Urrea

Lectura de 8 minutos
Publicado
03/10/2025

Cuando tocó hacer mantenimiento de una web con la versión de Drupal 10.2.5 sinceramente no esperaba que todo se rompiese porque “la caja tonta” resultó ser realmente tonta. Antes de empezar a contar como lo resolví debo aclarar un par de cosas, la primera es que puede haber soluciones mejores o peores a este bloqueo, pero no encontré absolutamente nada de documentación a fecha de un par de semanas antes de la publicación de este artículo; la segunda cosa que debo aclarar es tan sencilla como especificar que la actualización de Drupal era de la versión 10.2.5 a la 10.5.3 pasando por la 10.3.0 (Ya explicaré la relevancia de esto más adelante) con PHP 8.2, y MariaDB 10.7 en la base de datos como versiones de partida.

 

El iceberg de este barco. Actualizar una versión menor de las últimas versiones de Drupal no debería de ser algo costoso, al menos eso pensaba yo al tomar este desarrollo. Ya con todos los módulos actualizados a la versión más alta posible, y todo revisado, tocaba subir el núcleo de Drupal. Cambiar versiones y corregir dependencias a medida que saltaban errores en la actualización en frío, todo perfecto, los paquetes subían de versión sin problema. Limpiar cachés para que reconozca nuevos elementos y por supuesto actualizar la base de datos con drush updatedb, confirmar actualizaciones, y al llegar a un hook_update concreto (Del módulo book) fallaba con el siguiente error:

> [error] TypeError: Unsupported operand types: int + array in Drupal\Core\Config\TypedConfigManager->getDefinitionWithReplacements() (line 305 of /var/www/html/docroot/core/lib/Drupal/Core/Config/TypedConfigManager.php) #0

/var/www/html/docroot/core/lib/Drupal/Core/Config/TypedConfigManager.php(114): Drupal\Core\Config\TypedConfigManager->getDefinitionWithReplacements('weight', Array) > #1

/var/www/html/docroot/core/lib/Drupal/Core/Config/Schema/ArrayElement.php(172): Drupal\Core\Config\TypedConfigManager->buildDataDefinition(Array, 0, 'weight', Object(Drupal\Core\Config\Schema\Mapping)) > #2

/var/www/html/docroot/core/lib/Drupal/Core/Config/Schema/Mapping.php(52): Drupal\Core\Config\Schema\ArrayElement->buildDataDefinition(Array, 0, 'weight') > #3

/var/www/html/docroot/core/lib/Drupal/Core/Config/Schema/ArrayElement.php(56): Drupal\Core\Config\Schema\Mapping->getElementDefinition('weight') > #4

/var/www/html/docroot/core/lib/Drupal/Core/Config/Schema/ArrayElement.php(104): Drupal\Core\Config\Schema\ArrayElement->parse() > #5

Y un trazado largo de rutas, pero centrémonos en estos cinco primeros. Interesante depuración se llevó el método getDefinitionWithReplacements(), para acabar confirmando, como menciona correctamente el trazado, que la definición de tipo de dato weight trataba de agregar un array a un número entero, pero ¿Por qué?

 

¿Desde dónde y cuándo viene el campo de tipo weight? Mirando el registro de cambios del núcleo de Drupal, una interesante actualización de las definiciones del esquema de tipos de datos llegaron en la versión 10.3.0 agregando weight como un tipo de dato, heredando las propiedades del tipo de dato integer:

weight:
  type: integer
  label: 'Weight'
  constraints:
    Range:
      # @see PHP_INT_MIN (32-bit)
      min: -2147483648
      # @see PHP_INT_MAX (32-bit)
      max: 2147483647
    FullyValidatable: ~

Relacionando esto con el trazo del error anterior con un poco de depuración, parece ser que el tipo de dato weight debería de ser un array de metadatos del elemento, pero es 0 y al procesarlo se produce el error.

 

Al grano ¿Cómo puedo solucionarlo? En este caso particular la única salida que parecía viable era crear manualmente la definición del tipo de dato, en este caso weight, para ello hay que engancharse a los tipos de datos de la aplicación, para ello hay que crear en un módulo personalizado la siguiente clase /src/CustomModuleServiceProvider.php:

<?php

namespace Drupal\custom_module;

use Drupal\Core\DependencyInjection\ContainerBuilder;
use Drupal\Core\DependencyInjection\ServiceProviderBase;
use Drupal\custom_module\Service\WeightTypedConfigManagerService;

/**
 * Service provider to override core services.
 */
class CustomModuleServiceProvider extends ServiceProviderBase {

 /**
  * {@inheritdoc}
  */
 public function alter(ContainerBuilder $container) {
   if ($container->hasDefinition('config.typed')) {
     $definition = $container->getDefinition('config.typed');

     // {@inheritdoc}
     // @see \Drupal\custom_module\Service\WeightTypedConfigManagerService
     $definition->setClass(WeightTypedConfigManagerService::class);
   }
 }

}

Esto se enganchará a los servicios y posteriormente a los tipos de datos, aquí estableceremos la clase que también vamos a crear en /src/Service/WeightTypedConfigManagerService.php, aunque para este servicio no es necesario crear su definición en el archivo custom_module.services.yml:

<?php

namespace Drupal\custom_module\Service;

use Drupal\Core\Config\TypedConfigManager;
use Drupal\Core\StringTranslation\StringTranslationTrait;

/**
* @fix
* TypeError: Unsupported operand types: int + array in
* Drupal\Core\Config\TypedConfigManager->getDefinitionWithReplacements()
*
* @see https://www.drupal.org/node/3426319
*/
class WeightTypedConfigManagerService extends TypedConfigManager {

 use StringTranslationTrait;

 /**
  * {@inheritdoc}
  */
 public function getDefinitions() {
   $definitions = parent::getDefinitions();

   // Inject custom weight field definition if broken.
   if (array_key_exists('weight', $definitions) && !is_array($definitions['weight'])) {
     $definitions['weight'] = [
       'type' => 'integer',
       'label' => $this->t('Weight'),
       'constraints' => [
         'Range' => [
           'min' => PHP_INT_MIN,
           'max' => PHP_INT_MAX,
         ],
         'FullyValidatable' => NULL,
       ],
     ];
   }

   return $definitions;
 }

}

La definición es exactamente la misma a la que nos encontramos en /core/config/schema/core.data_types.schema.yml, y es que en este caso no hay que modificarla, sino simplemente agregarla y que el sistema la detecte y la instale. Ahora, al ejecutar drush updatedb, se ejecutan todos los hook_update sin producir el error anterior. Posteriormente, si el sistema detecta la definición de weight se puede eliminar este pequeño parche.

 

Conclusión. Este tipo de errores son muy interesantes a la vez que desafiantes, sobre todo si no existe ninguna documentación en Internet al respecto, pero siempre se puede implementar una solución personalizada y posteriormente probar su eliminación.
