The Drupal custom back-end cache

Drupal
Cache

Cloud, technology, web, Internet, business, developer, etc., from PxHere.

Pablo Urrea

15 minutes reading
Published
21/03/2025

In Drupal, the most commonly used cache is the one that affects the front-end, so that pages are cached or temporarily stored until a dynamic element changes, affecting the rendering of the page. However, this can also be replicated in the back-end thanks to back-end caching. This is useful, for example, when entity data is updated and needs to be re-requested when rendering a page. But what happens when the process does not have a direct connection to the front-end or requires individualized cache processing?

 

 

Back-end caching interface. Let’s take a simple example: a page contains a block that calls a custom service to request the states of a node of type “Request” and ultimately displays the total count of requests that are in a field of “Draft”, “Submitted”, “In progress”, “Accepted” or “Denied”. The service obtains all the processes in the system and adds values to each state to show the total count—easy so far. The system also finds it easy if it only has to check 100 requests, but what happens if there are 10,000 requests in the system? The system takes too long to respond, and the final page crashes because the service took too long to fetch and check the status of each request. What’s the solution? First, perform a query to the database to get the corresponding nodes by each state directly. Secondly, cache the response until one of these nodes changes. To do this, the back-end caching interface or CacheBackendInterface needs to be implemented. This can be directly integrated with

/** @var \Drupal\Core\Cache\CacheBackendInterface $cache */
$cache = \Drupal::cache();

Or it can also be injected as a dependency with the argument “@cache.default”.

  

Let’s cache the results! Once the back-end caching interface is implemented, the variable should be cached. This can be of any type, as Drupal will serialize it behind the scenes to store it. First, you need to define a cache ID. It is recommended to follow the pattern MODULE:FUNCTIONALITY/SERVICE/CLASS:FINAL_USE/METHOD:ENTITY_ID/ENTITY_UUID:LANGUAGE_IF_APPLICABLE. For example, a clear and concise ID would be my_site_tramites:summary_block:total_count:999:en, referring to the custom module my_site_tramites where the functionality is located, the block summary_block where the functionality resides, the functionality total_count, the parent page ID 999 where this block is located, and the applicable language en for the page.

Next, you need to check if there is any cached element with this cache ID. If it exists, its value will be stored in $cache_item in the following example to return or slightly process it:

if ($cache_item = $cache->get($cid)) {

If it doesn’t exist, after this if, the data processing will take place, and its calculation will be cached with

$cache->set($cid, $data, Cache::PERMANENT, $cache_tags);

But let’s break down the provided parameters to better understand how to obtain them correctly and provide them to the set method.

 

Cache ID. The unique cache ID to be stored. Its value in string can be anything, but to maintain order, it’s better to follow a pattern similar to the one mentioned earlier.

 

Data to cache. It can be of any type, string, integer, float, array, object (Be careful with very large objects that may exceed the database memory limit when serialized). Everything stored here will be retrieved when requesting the cache with the same ID.

 

Expiration. This value can be any integer between -1 and infinity, where -1 means that the cache never expires unless the cache tags expire, which I will discuss in the next point; 0 means that the cache is never stored because it expires immediately; and any other number is the timestamp when the cache will become invalid, for example, the timestamp for March 21, 2025, at 2:00 PM GMT is 1742565600. As a guide, the most commonly used constants are:

\Drupal\Core\Cache\Cache::PERMANENT

and

\Drupal\Core\Cache\CacheBackendInterface::CACHE_PERMANENT

Both have a value of -1.

 

Cache tags. These are tags by which the system identifies elements like entities and other resources to relate them to other items that depend on their cache. For example, the cache of a node with ID 25 would be node:25, when that node breaks its cache because it is updated, all items with the cache tag node:25 should be reloaded (along with the rest of the page). The set method of the back-end cache accepts a list of string tags as the last parameter. This list is usually initialized as array at the beginning of processing, and in each interaction with, for example, a node, the entity method getCacheTags() is called to obtain an array with the cache tags of this entity, along with the auxiliary class method \Drupal\Core\Cache\Cache::mergeTags() to which you can pass any number of cache tags arrays, and it will merge them into one, like this:

$cache_tags = \Drupal\Core\Cache\Cache::mergeTags($cache_tags, $node->getCacheTags());

Finally, provide $cache_tags to the back-end cache.

 

 

Conclusion. The proper and strategic use of back-end caching in Drupal is crucial for optimizing system performance, especially when handling large volumes of data. Implementing CacheBackendInterface allows efficient storage and retrieval of data, reducing processing load and improving page response times. By following best practices such as using well-structured cache identifiers, proper expiration management, and utilizing cache tags, it’s possible to ensure that the stored data is accurate and up to date when necessary. With a well-implemented caching strategy, the user experience and system stability can be significantly improved without compromising the integrity of the information.
