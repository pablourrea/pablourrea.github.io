Migrate Content Paragraphs with Migrate

Drupal
Migrate

How do birds know how to migrate? - The Daily Illini

Pablo Urrea

20 minutes reading
Published
18/03/2024
Updated
12/09/2024

The other day I was proposed to migrate content from a website on Drupal 7 to another on Drupal 10 simply because it was easier to renovate it than to update it. And I, being an expert in saying yes without knowing the swamp I was getting into, started analyzing how I could do it.


In search of enlightenment. In the meantime, the idea arose to build a view in Drupal 7 that provides absolutely all the fields of a content type in JSON format. So far, so simple, right? You configure a YML file for migration with the appropriate plugins, and there you go, the entities were copied from one system to another. It turns out that the data structure has changed in the last 10 years (What a surprise), and now certain content blocks that used to be stored in the entity itself are stored as Paragraph type entities. I thought, okay, I'll migrate the Paragraph entities, add the migration as a dependency of the main entity, and add the migration plugin, and nothing happened here. Then I encountered a wonderful bidirectionality here: The parent entity needed to have the Paragraph referenced, and the Paragraph needed to have the parent entity referenced (along with other parent data).

The problem was that I couldn't migrate it like this with the default migrate plugin because it only added the reference in one of the entities: If I added the Paragraph as a dependency of the entity, this did not have a reference to the parent, and vice versa. This battle lasted three long days until I came up with a solution worthy of Miguel Ángel (For sculpting and all that): Chisel the database when migrating Paragraphs so that both entities matched.


NOTE: The process of migrating entities with the inclusion of paragraphs is a complex task that requires a meticulous approach and a deep understanding of data structure and entity relationships. In this extension, we will delve into the different aspects involved in this process, from identifying associated paragraphs to updating the database and verifying the integrity of the migrated data.

 

Getting hands dirty. In order to have all the data post migration, it was best to create an Event Subscriber, starting with the basic configuration in the module.services.yml file:

services:
 module.migration_finished_subscriber:
   class: Drupal\module\EventSubscriber\MigrateParagraphsEventSubscriber
   tags:
     - { name: event_subscriber }

And its corresponding class in the src/EventSubscriber/MigrateParagraphsEventSubscriber.php file:

class MigrateParagraphsEventSubscriber implements EventSubscriberInterface {
  public static function getSubscribedEvents() {
    $events[MigrateEvents::POST_IMPORT][] = ['postImport'];
    return $events;
  }
  public function postImport(MigrateImportEvent $event) {
  }
}

With this configuration and a cache flush, after running any migration, the code of the postImport method will be executed.

 

Leaving breadcrumbs. Now, we need to identify the migration processes of Paragraphs in the parent entity, in order to have both entities consolidated in the database: The parent entity, and the Paragraph.

For this, the simplest thing is to add an identifying property to the process:

field_paragraphs/target_id:
  plugin: migration_lookup
  migration: module_migrate_paragraphs
  migrate_paragraphs: true
  source: id

From this configuration, the ID of the entities migrated in the first migration (the Paragraphs) would be obtained based on a common ID from the data source, with the added property migrate_paragraphs: true to identify in the process that this process requires matching the Paragraph entities from the previous migration with those migrated in the current configuration.


Getting hands dirty. Now we need to identify the fields that require a Paragraph migration. To do this, we need to obtain the migration object from the event, and its process in array format:

$migration = $event->getMigration();
$migration_process = $migration->getProcess();

Now comes the fun part, "processing the process":

protected function searchMigrationParagraphKeyValueInProcessArray(array $values, string|int $key = 0, string $value = ''): mixed {
  foreach ($values as $vkey => $vvalue) {
    if ($vkey === $key && $vvalue == $value) {
      return $vkey;
    }
    else {
      if (is_array($vvalue)) {
        $found = $this->searchMigrationParagraphKeyValueInProcessArray($vvalue, $key, $value);
        if ($this->paragraph_path_found === TRUE) {
          $this->paragraph_fields[$vkey] = [
            'field' => $vkey,
            'migration' => $found,
          ];
          $this->paragraph_path_found = FALSE;
        }
        if ($found === $key) {
          $this->paragraph_path_found = TRUE;
          return (!empty($vvalue['migration'])) ? $vvalue['migration'] : $values;
        }
      }
    }
  }
  return '';
 }

This wonderful method iterates recursively over all processes in an array, and saves the field name of those containing the property migrate_paragraphs: true in the list $this->paragraph_fields.

Red pill, blue pill. It is important to note that this process only provided us with the ID of the entity, which can be of any type, so it must be parsed from the configuration of the destination plugin or Destination Plug-in the ID of the entity type on which we must load the ID we obtained. For this, there are two methods, one more reliable than the other, although for this example I have included both to ensure their obtainment. The first method consists of obtaining through regular expression the value of the ID of the Destination Plug-in the rightmost value, coinciding in 99.99% of cases (Source: Times New Roman) with the entity type, of course, in most cases coinciding with the value "node". To see it better, the regular expression obtains the highlighted value of "entity:node", making it possible through Entity Type Manager to obtain the node by its ID. If this process is not possible, the Entity Type Manager would throw an exception in which we will process the second less reliable method: Obtaining the provider of the definition of the Destination Plug-in, this method can fail in the case of sub entities like Paragraphs, so it is best to start with the first method. The try-catch defined in the following block explains how to implement both methods and resort to the second in case of failure of the first:

$migration_destination_plugin = $migration->getDestinationPlugin();
$migration_destination_plugin_definition = $migration_destination_plugin->getPluginDefinition();
try {
  preg_match($this->match_entity_regex, $migration_destination_plugin_definition['id'], $entity_type);
  $entity_type = $entity_type[1];
  $entity = \Drupal::entityTypeManager()->getStorage($entity_type)->load($source_data->{$this->migrate_db_target_id_column});
}

The icing on the cake. Finally, the ID of the Paragraphs that must be matched with the parent entity is obtained from the referenced table of migrated entities. The language to associate the Paragraph is loaded, by default it can be associated with the main language of the site, and the corresponding value of the base data table of Paragraphs is updated to establish the parent entity, the language of the Paragraph, and some more data.

  ->condition('mm.'. $this->migrate_db_source_id_column, $source_data->{$this->migrate_db_source_id_column})
  ->fields('mm', [$this->migrate_db_target_id_column, $this->migrate_db_source_id_column])
  ->execute()
  ->fetchAllAssoc($this->migrate_db_target_id_column);
foreach ($paragraphs as $paragraphs_source_data) {
  if (!empty($paragraphs_source_data->{$this->migrate_db_target_id_column})) {
    $default_language = $this->language_manager->getDefaultLanguage();
    $default_language_id = $default_language->getId();
    $entity_langcode = ($entity->hasField('langcode') && $entity->langcode->value) ? $entity->langcode->value : 'und';

      ->condition('id', $paragraphs_source_data->{$this->migrate_db_target_id_column})

And, although this task has been theoretically performed by Migrate, to put the icing on the cake, we load the paragraph and associate it with the field of the parent entity if it is not already.

Conclusion. Content migration, especially when it involves complex entities like Paragraphs in Drupal, can be a challenging process. However, with a solid understanding of the processes involved and the available tools, successful migrations are possible.

May 9, 2024 Update

Since I published this article (and previously completed this development), I've had a nagging feeling of code improvement. That's why we have decided to do tests by rewriting the searchMigrationParagraphKeyValueInProcessArray() method from scratch.


The simplest is the most efficient. Really, the best way to avoid the use of class attributes is by using the extreme simplification of the method's own recursion so that the recursion itself does not delay the process:

protected function searchMigrationParagraphKeyValueInProcessArray(array $values, string $value, string $field = '', string $key = 'migrate_paragraphs'): array {
   $paragraphs_found_list = [];
   foreach ($values as $vkey => $vvalue) {
     if (is_array($vvalue)) {
       if (is_string($vkey) && strlen($vkey) > 0) {
         $field = $vkey;
       }
       $paragraphs_found_list = array_merge($paragraphs_found_list, $this->searchMigrationParagraphKeyValueInProcessArray($vvalue, $value, $field, $key));
     }
     elseif ($vkey === $key && (string) $vvalue === $value && isset($values['migration']) && is_string($values['migration'])) {
       $paragraphs_found_list[$field] = [
         'migration' => $values['migration'],
       ];
       continue;
     }
   }
   return $paragraphs_found_list;
 }

This allows eliminating the attributes related to the $this->identifier, $this->paragraph_fields, and $this->paragraph_path_found method.
You also need to update the initial method call to adapt it to the results and the return variable, which will now always be of type array, replacing

   $this->searchMigrationParagraphKeyValueInProcessArray($migration_process, $this->identifier, TRUE);
   if (!empty($this->paragraph_fields)) {
     foreach ($this->paragraph_fields as $paragraph_field) {
       if (empty($paragraph_field['field']) || empty($paragraph_field['migration'])) {
         continue;
       }
       if (preg_match($this->match_field_name_regex, $paragraph_field['field'], $matches)) {

with

   $paragraph_fields = $this->searchMigrationParagraphKeyValueInProcessArray($migration_process, (string) TRUE);
   if (!empty($paragraph_fields)) {
     foreach ($paragraph_fields as $paragraph_field_name => $paragraph_field) {
       if (!is_string($paragraph_field_name) || !is_string($paragraph_field['migration'])) {
         continue;
       }
       if (preg_match($this->match_field_name_regex, $paragraph_field_name, $matches)) {

 

Additionally, as an improvement, you can apply the $this->migrate_db_prefix attribute (which was not being applied with the value "migrate_map_"); and as a bug fix, you can remove the $this->match_entity_regex attribute since it was only used once (It's best to apply the regular expression or RegEx directly as a string within the PHP preg_match function).

Update from May 29, 2024

After conducting multiple migration tests for different types of entities, there were cases where an error occurred in the row because the entity was skipped in different scenarios (entity translation, nested paragraphs, etc.), something I have corrected.


It's better to let go than to hold on to the fatal error. In reality, debugging code is very healthy and saves a lot of time (even if it is not always pleasant). This led me to the last block of code, where the database is chiseled so that the paragraph does not become orphaned, and the parent entity is updated so that it does not remain childless. In specific cases where it cannot find the child's ID, it tries to update both and then ends the process, losing the entity and risking the continuity of the migration.

                    if (!empty($paragraphs)) {
                      foreach ($paragraphs as $paragraphs_source_data) {
                        if (!empty($paragraphs_source_data->{$this->migrate_db_target_id_column})) {
                          // It is assumed that the website's default language is the same as the entity's default language.
                          // This is used only to define if the Paragraph translation is the default translation.
                          /** @var \Drupal\Core\Language\LanguageInterface $default_language */
                          $default_language = $this->language_manager->getDefaultLanguage();
                          $default_language_id = $default_language->getId();
                          $entity_langcode = ($entity->hasField('langcode') && $entity->langcode->value) ? $entity->langcode->value : 'und';
                          // Update the Paragraph values to have the entity field as parent.
                          $this->database->update('paragraphs_item_field_data')
                            ->fields([
                              'langcode' => $entity_langcode,
                              'parent_id' => $source_data->{$this->migrate_db_target_id_column},
                              'parent_type' => $entity_type,
                              'default_langcode' => ($default_language_id == $entity_langcode) ? 1 : 0,
                              'parent_field_name' => $field_name,
                              'content_translation_source' => $default_language_id,
                            ])
                            ->condition('id', $paragraphs_source_data->{$this->migrate_db_target_id_column})
                            ->execute();
                          /** @var \Drupal\paragraphs\ParagraphInterface|null $paragraph */
                          $paragraph = Paragraph::load($paragraphs_source_data->{$this->migrate_db_target_id_column});
                          // For security reasons, check that the reference to the Paragraph
                          // in the entity field is not duplicated and consolidate its reference.
                          if ($paragraph instanceof ParagraphInterface && $entity->hasField($field_name) && !$this->isParagrahDuplicated($entity, $paragraph, $field_name)) {
                            $entity->{$field_name}->appendItem($paragraph);
                            $entity->save();
                          }
                        }
                      }
                    }

 

The best solution has been implemented for a long time. The best way to detect errors and continue the migration without major incidents is to implement in this case a try-catch both in chiseling the database and updating the parent entity. But going a step further and improving the system to perform fewer database updates, chiseling can be included after validating the existence of the paragraph, thus avoiding repetitions and unnecessary updates, replacing the previous block with:

                    if (!empty($paragraphs)) {
                      foreach ($paragraphs as $paragraphs_source_data) {
                        if (!empty($paragraphs_source_data->{$this->migrate_db_target_id_column})) {
                          /** @var \Drupal\paragraphs\ParagraphInterface|null $paragraph */
                          $paragraph = Paragraph::load($paragraphs_source_data->{$this->migrate_db_target_id_column});
                          // For security reasons, check that the reference to the Paragraph
                          // in the entity field is not duplicated and consolidate its reference.
                          if ($paragraph instanceof ParagraphInterface && $entity->hasField($field_name) && !$this->isParagrahDuplicated($entity, $paragraph, $field_name)) {
                            try {
                              // It is assumed that the website's default language is the same as the entity's default language.
                              // This is used only to define if the Paragraph translation is the default translation.
                              /** @var \Drupal\Core\Language\LanguageInterface $default_language */
                              $default_language = $this->language_manager->getDefaultLanguage();
                              $default_language_id = $default_language->getId();
                              $entity_langcode = ($entity->hasField('langcode') && $entity->langcode->value) ? $entity->langcode->value : 'und';
                              // Update the Paragraph values to have the entity field as parent.
                              $this->database->update('paragraphs_item_field_data')
                                ->fields([
                                  'langcode' => $entity_langcode,
                                  'parent_id' => $source_data->{$this->migrate_db_target_id_column},
                                  'parent_type' => $entity_type,
                                  'default_langcode' => ($default_language_id == $entity_langcode) ? 1 : 0,
                                  'parent_field_name' => $field_name,
                                  'content_translation_source' => $default_language_id,
                                ])
                                ->condition('id', $paragraphs_source_data->{$this->migrate_db_target_id_column})
                                ->execute();
                            }
                            catch (\Exception $e) {
                              $this->logger->error($e->getMessage());
                            }
                            try {
                              $entity->{$field_name}->appendItem($paragraph);
                              $entity->save();
                            }
                            catch (\Exception $e) {
                              $this->logger->error($e->getMessage());
                            }
                          }
                        }
                      }
                    }

Within the catch, you can see the implementation of Drupal's logger system. To add it, it is as simple as adding the service @logger.factory to the event subscriber in the services.yml file, adding the dependency Drupal\Core\Logger\LoggerChannelFactory to the event subscriber, including within this the object to log errors

 /**
  * The logger channel.
  *
  * @var \Drupal\Core\Logger\LoggerChannelInterface
  */
 protected $logger;

and updating the class constructor to associate the service with the object:

  /**
   * Constructor.
   *
   * @param \Drupal\Core\Database\Connection $database
   *   The database connection.
   * @param \Drupal\Core\Logger\LoggerChannelFactory $logger
   *   The logger channel.
   * @param \Drupal\Core\Language\LanguageManagerInterface $language_manager
   *   The language manager.
   * @param \Drupal\Core\Entity\EntityTypeManagerInterface $entity_type_manager
   *   The entity type manager.
   */
  public function __construct(Connection $database, LoggerChannelFactory $logger, LanguageManagerInterface $language_manager, EntityTypeManagerInterface $entity_type_manager) {
    $this->database = $database;
    $this->language_manager = $language_manager;
    $this->logger = $logger->get('module');
    $this->entity_type_manager = $entity_type_manager;
  }

This last step is optional. If you do not want to log errors during the migration, you can simply leave the catch empty.
