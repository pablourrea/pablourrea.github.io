Selective entity update during Drupal migrations

Drupal
Migrate

Athlete jumping over hurdles

Pablo Urrea

5 minutes reading
Published
25/08/2024

Sometimes, Drupal migrations need to update entities instead of creating them using the migration parameter --update. During this process, all entities from the previous migration will be updated, along with the possible creation of new entities. For better or worse, the new data will update all available entities in the system and data source. But what if it is necessary to update data for only some entities?

 

The unit method. If you need to update only a few entities, but not too many, you can add the --idlist parameter to the migration command, followed by the migration identifiers corresponding to each data group. For example, if you have the following data in JSON format:

{
  "elements": [
    {
      "element": {
        "id": "1",
        "name": "Name 1"
      },
      "element": {
        "id": "2",
        "name": "Name 2"
      },
      "element": {
        "id": "3",
        "name": "Name 3"
      },
      "element": {
        "id": "4",
        "name": "Name 4"
      },
    }
  ]
}

With this data injected into a migration, if you only need to migrate elements with id's 1, 2, and 3, the parameter would be --idlist=1,2,3. Applied to a full migration command with drush, it would look like this:

drush migrate-import migrate_elements --idlist=1,2,3

If instead of creating them, you need to update them, the command would look like this with the --update parameter:

drush migrate-import migrate_elements --update --idlist=1,2,3

This way of migrating individual entities is very simple and fast, but it is only applicable to a small number of identifiers (unless you feel like entering 1000 IDs into the command parameter, which a generative AI might handle well, but you'd have to see how the system supports it).

 

 

The collective method. Let's propose the following case: “The editor needs you to migrate many, many, too many entities, a ton of entities. And this editor will individually check that all entities have been migrated correctly and would like to 'lock' somehow the entities that have been migrated correctly and update the data source for entities that were not migrated well.” And you wonder if there is a way to update all entities except the locked ones. Well, the first thing would be to create a boolean field (TRUE or FALSE) that decides if an entity is locked or not, and now, the following custom Migrate plugin will check in the database if the entity in the current Row has already been migrated, and the value provided for the field provided in the field and value parameters of the plugin:

/**
 * Migrate plugin that returns NULL if it finds the field next to the provided value or TRUE.
 * These return variables facilitate further processing such as skipping the row, for example.
 * It does not need a source and generates its own return value.
 *
 * @MigrateProcessPlugin(
 *   id = "check_entity_field_value"
 * )
 *
 * Example usage:
 * @code
 * check_entity_field_value_example:
 *   plugin: check_entity_field_value
 *   field: field_to_check
 *   value: value_to_check
 * @endcode
 */
class CheckEntityFieldValue extends ProcessPluginBase implements ContainerFactoryPluginInterface {

  /**
   * The migration.
   *
   * @var \Drupal\migrate\Plugin\MigrationInterface|null
   */
  protected $migration;

  /**
   * The entity type manager.
   *
   * @var \Drupal\Core\Entity\EntityTypeManagerInterface
   */
  protected $entity_type_manager;

  /**
   * {@inheritdoc}
   */
  public static function create(ContainerInterface $container, array $configuration, $plugin_id, $plugin_definition, MigrationInterface $migration = NULL) {
    $instance = new static($configuration, $plugin_id, $plugin_definition);
    $instance->entity_type_manager = $container->get('entity_type.manager');
    $instance->migration = $migration;

    return $instance;
  }

  /**
   * {@inheritdoc}
   */
  public function transform($value, MigrateExecutableInterface $migrate_executable, Row $row, $destination_property): bool|null {
    /** @var \Drupal\Core\Entity\EntityTypeInterface|string $entity_type */
    $entity_type = $this->getMigrationTargetEntityType($this->migration);
    $field = (isset($this->configuration['field']) && is_string($this->configuration['field'])) ? $this->configuration['field'] : NULL;
    if (isset($entity_type) && isset($field)) {
      $destination_ids = $this->getEntityIdsFromRow($row);
 
      if (!empty($destination_ids)) {
        $value = (isset($this->configuration['value'])) ? $this->configuration['value'] : NULL;
        foreach ($destination_ids as $entity_id) {
          if (!$entity_id) {
            continue;
          }

          /** @var \Drupal\Core\Entity\EntityInterface|null $entity */
          $entity = $this->entity_type_manager->getStorage($entity_type)->load($entity_id);
          if ($entity instanceof FieldableEntityInterface && $entity->hasField($field)) {
            // Returns NULL if it finds the field with any value
            // if the value is not specified, or if it is equal
            // to the value if the value has been specified.
            if ((isset($this->configuration['value']) && ((isset($entity->$field->value) && $entity->$field->value == $this->configuration['value']) || (isset($entity->$field->target_id) && $entity->target_id == $this->configuration['value']))) || (!isset($this->configuration['value']) && (isset($entity->$field->value) || isset($entity->$field->target_id)))) {
              return NULL;
            }
          }
        }
      }
    }

    return TRUE;
  }

  /**
   * Retrieves the target entity type for a given migration.
   *
   * @param \Drupal\migrate\Plugin\MigrationInterface $migration
   *   The migration object from which to retrieve the target entity type.
   *
   * @return string|null
   *   The target entity type if it can be determined.
   *
   * @throws \Exception $e
   */
  protected function getMigrationTargetEntityType(MigrationInterface $migration): string|null {
    try {
      /** @var \Drupal\migrate\Plugin\MigrateDestinationInterface $migration_destination_plugin */
      $migration_destination_plugin = $migration->getDestinationPlugin();
      /** @var \Drupal\Component\Plugin\Definition\PluginDefinitionInterface|array $migration_destination_plugin_definition */
      $migration_destination_plugin_definition = $migration_destination_plugin->getPluginDefinition();

      // Gets from the plugin definition the id of the target entity,
      // it will always be the first match or none.
      preg_match('/:([^:]+)$/', $migration_destination_plugin_definition['id'], $entity_type);

      return (isset($entity_type[1]) && is_string($entity_type[1])) ? $entity_type[1] : NULL;
    }
    catch (\Exception $e) {
      return NULL;
    }
  }

  /**
   * Retrieves destination entity IDs from a migration row.
   *
   * @param \Drupal\migrate\Row $row
   *   The migration row object from which to retrieve the entity IDs.
   *
   * @return array
   *   An associative array of destination ID values.
   */
  protected function getEntityIdsFromRow(Row $row): array {
    $destination_ids = [];
    $mid_map = $row->getIdMap();
    if (!empty($mid_map)) {
      foreach ($mid_map as $mid_map_element => $mid_map_element_value) {
        // Destination IDs are always added with the same ID
        // and a counter (destid1, destid2, destid3, etc.).
        if (str_contains($mid_map_element, 'destid')) {
          $destination_ids[$mid_map_element] = $mid_map_element_value;
        }
      }
    }

    return $destination_ids;
  }
}

This plugin, for each Row, first gets the field parameter and the entity type to check using the getMigrationTargetEntityType() method with the current migration of the destination data using a regular expression. Then, it retrieves, if it exists, the destination entity with the getEntityIdsFromRow() method, which will need the current row to get raw data from the database; this result will only contain values if it is a migration update. Once this data is obtained, the destination entity can be loaded, and it can be checked if the field, if present, has the specified value.

 

Now you would need to add the plugin according to the example to the migration. For instance, if you need to skip the entity when the boolean field field_migrate_skip contains the value TRUE, the plugin will be defined as follows:

skip_row_on_field_migrate_skip_true:
  -
    plugin: check_entity_field_value
    field: field_migrate_skip
    value: TRUE
  -
    plugin: skip_on_empty
    method: row
    message: 'Ignored because field field_migrate_skip is TRUE.'

This will skip the Row of the migration if the value of the field_migrate_skip field is equal to TRUE because the plugin will return NULL, and the skip_on_empty plugin will identify it as an empty value. Otherwise, it will receive TRUE and will not skip the Row, leaving the entities “locked” by the editor intact.

Although this is a fictional case, it has many applications, such as a mass update of entities by providing a field value if certain conditions are met.

 

 

Conclusion. Whether you need to update a few entities during a migration or skip just a few, there are different methods to perform this data update. It is only necessary to consider which method is most convenient for the migration's needs.
