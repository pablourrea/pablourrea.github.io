Definition of the weight data type in Drupal

Pablo Urrea

8 minutes reading
Published
03/10/2025

When it was time to perform maintenance on a website running Drupal 10.2.5, I honestly did not expect everything to break because “the dumb box” turned out to be really dumb. Before I start explaining how I solved it, I need to clarify a couple of things. The first is that there may be better or worse solutions to this block, but I found absolutely no documentation as of a couple of weeks before this article was published; the second thing I need to clarify is as simple as specifying that the Drupal update was from version 10.2.5 to 10.5.3 passing through 10.3.0 (I will explain the relevance of this later) with PHP 8.2 and MariaDB 10.7 as the starting database versions.

 

The iceberg of this ship. Updating a minor version of the latest Drupal versions should not be costly, at least that’s what I thought when taking on this development. With all modules updated to the highest possible version and everything checked, it was time to upgrade the Drupal core. Changing versions and fixing dependencies as errors popped up during the cold update—everything went perfectly, packages upgraded without issues. Clearing caches so new elements are recognized and, of course, updating the database with drush updatedb, confirming updates, and when reaching a specific hook_update (from the book module) it failed with the following error:

> [error] TypeError: Unsupported operand types: int + array in Drupal\Core\Config\TypedConfigManager->getDefinitionWithReplacements() (line 305 of /var/www/html/docroot/core/lib/Drupal/Core/Config/TypedConfigManager.php) #0

/var/www/html/docroot/core/lib/Drupal/Core/Config/TypedConfigManager.php(114): Drupal\Core\Config\TypedConfigManager->getDefinitionWithReplacements('weight', Array) > #1

/var/www/html/docroot/core/lib/Drupal/Core/Config/Schema/ArrayElement.php(172): Drupal\Core\Config\TypedConfigManager->buildDataDefinition(Array, 0, 'weight', Object(Drupal\Core\Config\Schema\Mapping)) > #2

/var/www/html/docroot/core/lib/Drupal/Core/Config/Schema/Mapping.php(52): Drupal\Core\Config\Schema\ArrayElement->buildDataDefinition(Array, 0, 'weight') > #3

/var/www/html/docroot/core/lib/Drupal/Core/Config/Schema/ArrayElement.php(56): Drupal\Core\Config\Schema\Mapping->getElementDefinition('weight') > #4

/var/www/html/docroot/core/lib/Drupal/Core/Config/Schema/ArrayElement.php(104): Drupal\Core\Config\Schema\ArrayElement->parse() > #5

And a long trace of paths, but let's focus on these first five. The method getDefinitionWithReplacements() went through interesting debugging, ultimately confirming, as the trace correctly shows, that the weight data type definition was trying to add an array to an integer, but why?

 

Where and when does the weight field come from? Looking at the Drupal core changelog, an interesting update to the data type schema definitions arrived in version 10.3.0, adding weight as a data type, inheriting the properties of the integer type:

weight:
  type: integer
  label: 'Weight'
  constraints:
    Range:
      # @see PHP_INT_MIN (32-bit)
      min: -2147483648
      # @see PHP_INT_MAX (32-bit)
      max: 2147483647
    FullyValidatable: ~

Relating this to the previous error trace with some debugging, it seems that the weight data type should be a metadata array of the element, but it is 0, and processing it produces the error.

 

Getting straight to the point: how can I fix it? In this particular case, the only viable solution seemed to be manually creating the data type definition, in this case weight. To do this, you need to hook into the application's data types by creating the following class in a custom module at /src/CustomModuleServiceProvider.php:

<?php

namespace Drupal\custom_module;

use Drupal\Core\DependencyInjection\ContainerBuilder;
use Drupal\Core\DependencyInjection\ServiceProviderBase;
use Drupal\custom_module\Service\WeightTypedConfigManagerService;

/**
 * Service provider to override core services.
 */
class CustomModuleServiceProvider extends ServiceProviderBase {

 /**
  * {@inheritdoc}
  */
 public function alter(ContainerBuilder $container) {
   if ($container->hasDefinition('config.typed')) {
     $definition = $container->getDefinition('config.typed');

     // {@inheritdoc}
     // @see \Drupal\custom_module\Service\WeightTypedConfigManagerService
     $definition->setClass(WeightTypedConfigManagerService::class);
   }
 }

}

This hooks into the services and subsequently the data types. Here we will set the class, which we will also create in /src/Service/WeightTypedConfigManagerService.php, although for this service it is not necessary to define it in the custom_module.services.yml file:

<?php

namespace Drupal\custom_module\Service;

use Drupal\Core\Config\TypedConfigManager;
use Drupal\Core\StringTranslation\StringTranslationTrait;

/**
* @fix
* TypeError: Unsupported operand types: int + array in
* Drupal\Core\Config\TypedConfigManager->getDefinitionWithReplacements()
*
* @see https://www.drupal.org/node/3426319
*/
class WeightTypedConfigManagerService extends TypedConfigManager {

 use StringTranslationTrait;

 /**
  * {@inheritdoc}
  */
 public function getDefinitions() {
   $definitions = parent::getDefinitions();

   // Inject custom weight field definition if broken.
   if (array_key_exists('weight', $definitions) && !is_array($definitions['weight'])) {
     $definitions['weight'] = [
       'type' => 'integer',
       'label' => $this->t('Weight'),
       'constraints' => [
         'Range' => [
           'min' => PHP_INT_MIN,
           'max' => PHP_INT_MAX,
         ],
         'FullyValidatable' => NULL,
       ],
     ];
   }

   return $definitions;
 }

}

The definition is exactly the same as found in /core/config/schema/core.data_types.schema.yml. In this case, it doesn’t need to be modified, just added so that the system detects and installs it. Now, running drush updatedb executes all hook_update operations without producing the previous error. Later, if the system detects the weight definition, this small patch can be removed.

 

Conclusion. These types of errors are very interesting as well as challenging, especially when no documentation exists online, but a custom solution can always be implemented and later tested for removal.
