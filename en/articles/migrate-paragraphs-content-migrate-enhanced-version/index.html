Migrate Paragraphs of Content with Migrate (Enhanced version)

Drupal
Migrate

How do birds know how to migrate?

Pablo Urrea

5 minutes reading
Published
10/08/2024

In the article Migrate Content Paragraphs with Migrate, I explore the possibilities of migrating Paragraphs in Drupal using migration configuration files that are independent of the parent node. However, although Paragraphs are an entity, they are not a primary entity and always depend on a parent. In this article, I show how to migrate Paragraphs and link them to the parent within the same migration, thus optimizing the migration process by reducing execution time, eliminating dependencies, and strengthening the parent-child relationship between the two entities, making this process a more convenient method than the one discussed in the previous article.

 

Dependencies. To use this method, it is necessary to install the module for Drupal: Migrate Child Entity Generate. You can install it from the “Extend” section of the Drupal administrator or with Composer:

composer require drupal/migrate_child_entity_generate

And enable it from the “Extend” section of the Drupal administrator or with Drush:

drush en migrate_child_entity_generate

 

One Migrate plugin to rule them all. Using the child_entity_generate plugin from the Migrate Child Entity Generate module is very simple. You need to define the plugin, the entity type, the bundle type, and optionally define the variable and default constant values as in the following example:

field_name:
  plugin: child_entity_generate
  entity_type: paragraph
  bundle: paragraph_bundle
  values:
    field_1: value_1
    field_2/value: value_2
  default_values:
    langcode: "en"
    field_2/format: "text"

The difference between values and default_values is that in values, you introduce variable values for each different Paragraph (e.g., a text, a date, etc.), while in default_values, you introduce static and common values for all Paragraphs (e.g., the format of a CKEditor WYSIWYG field, a language selection field, etc.).

 

One Migrate plugin to rule all values. Unlike the entity_generate plugin from the Migrate Plus module, the child_entity_generate plugin does accept an array of values as a parameter, for example:

destination:
 plugin: "entity:node"
source:
 fields:
   -
     faq_items:
       -
         question: "Some question"
         answer: "Some answer"
       -
         question: "Another question"
         answer: "Another answer"
process:
 field_faqs:
   plugin: child_entity_generate
   source: faq_items
   entity_type: field_collection
   bundle: faq
   values:
     field_faq_question: question
     field_faq_answer/value: answer
   default_values:
     field_faq_answer/format: "basic_html"

The above code would create a faq_items entity of type faq for each item in the array faq_items, assigning the value of question to the field_faq_question field and the value of answer to the field_faq_answer field, with the basic_html format as the default value for the field_faq_answer field for all entities. It would then assign the target_id and target_revision_id of each entity to the field_faqs field.

 

ℹ️
As of the publication of this article, the Migrate Child Entity Generate module in the stable version 1.0.1 from June 4, 2024, does not accept references to fields from the current Row in the migration process (e.g., assigning "@other_field" to a field). To fix this, I created a patch that the module maintainer accepted in the issue "Refine the process value filtering so that it gets values from the row". If you need it, you can apply the following patch or install the development version 1.x-dev of the module.

 

Conclusion. Efficiently migrating Paragraphs in Drupal is a challenge, but using the Migrate Child Entity Generate module offers a powerful solution. Through this method, it is possible to integrate Paragraphs directly with their parent nodes in a single migration. Additionally, the child_entity_generate plugin provides a robust and effective method for migrating Paragraphs in Drupal.
